# 「おまかせ」モードの学習

アプリの「おまかせ」モードは、たくさんの写真から「HDR のデータをどう仕上げれば写真らしく見えるか」を学習した小さなモデルで合成します。
このフォルダには、そのデータ作り・学習・書き出し・評価のコード一式が入っています。
学習済みの重みは `src/models/tone-hdrplus.bin`（約 540KB）で、アプリはこれを読み込むだけなので、普段使う分には何もする必要はありません。

## 学習データ

[HDR+ Burst Photography Dataset](https://hdrplusdata.org/)（Google, Hasinoff et al. 2016, CC BY-SA）を使います。

- スマートフォン（Nexus / Pixel）で撮った 3,640 シーン。逆光・夜景・室内など明暗差の大きい場面が多い
- 各シーンに **位置合わせ・合成済みの RAW（merged.dng）** と、Google カメラの HDR+ が仕上げた **完成写真（final.jpg）** がある
- merged.dng は「露出を抑えて撮った、白飛びしていないリニアな HDR データ」で、AEB を合成した放射輝度マップとほぼ同じ性質を持つ
- つまり「リニアな HDR → 写真らしい仕上がり」の手本が 3,640 組ある。HDRNet（Gharbi et al. 2017）も同じデータで HDR+ の仕上げを学習している

`prepare_hdrplus.py` は 1 シーン約 20MB を順にダウンロード → 現像 → 縮小して保存し、元データはすぐ捨てます（全体で 70GB 超あるため）。

- merged.dng は HDR+ の README どおりに現像します（黒/白レベル → レンズシェーディング補正 → AsShotNeutral の WB → rgb2rgb 行列 → リニア sRGB）
- 縦位置・上下逆さまの写真は、final.jpg との相関が最大になる向きを自動で選びます
- デジタルズームで撮ったシーン（final.jpg が中央の拡大）は、倍率と位置を探索して切り出しを合わせます
- 画素単位で揃っていることを勾配の相関で確かめ、揃わないものは除外します
- キュレーション済みの 153 シーン（`20171106_subset`）は **評価専用** にして学習には使いません

## モデル

HDRNet を輝度だけに絞って小さくしたものです（約 27 万パラメータ）。

```
放射輝度（リニア RGB） ─┬─ 256×256 に縮小 → log2 − 中央値 → CNN → 双方向グリッド [係数 3][明るさ 8 段][16][16]
                        │                                                  │
                        └─ 各画素の対数輝度 ln ──→ ガイド曲線 ──→ (x, y, 明るさ) で 3 次元補間
                                                                           ↓
                                  lout = a·ln + b（傾き a・オフセット b）、彩度 s
                                  → 輝度だけにゲインを掛け（色相はそのまま）→ 肩特性 → sRGB → 彩度
```

- **エッジを保つ局所トーンマッピング**: 係数は位置だけでなく明るさの段ごとに違うので、明暗の境目をまたいで混ざらず、ハロ（縁の光輪）が出にくい
- **解像度に依存しない**: CNN は常に 256×256 を見て、フル解像度の画素はグリッドを補間するだけ。プレビューと書き出しで同じグリッドを使う
- **色相は変えない**: 輝度と彩度だけを変えるので、HDR+（Pixel）の色作りやホワイトバランスを Canon の RAW に持ち込まない
- **露出に依存しない**: 入力は中央値で正規化するので、明るさの決め方は画像の内容（ヒストグラムの形や配置）から学習する
- **階調の逆転を防ぐ**: 各セルのトーンカーブが単調増加になるよう学習時に罰則を入れている（雲より空が暗くなる、のような不自然さを防ぐ）

## 使い方

```bash
cd training
python -m venv venv && . venv/bin/activate
pip install -r requirements.txt           # CPU 版の PyTorch で十分

NPROC=6 python prepare_hdrplus.py data    # データ作り（数十分、出力は約 7GB）
python train.py --data data/train --out runs/v1 --epochs 40
python export_model.py runs/v1/best.pt ../src/models/tone-hdrplus.bin --fixture ../test/fixtures/learned.json
cd .. && npm test                         # TypeScript 実装が PyTorch と一致するか確認
```

### 評価

学習に使っていない 153 シーンから、カメラの AEB（−2 / 0 / +2 EV、平均測光）を模したブラケットを作り、
**アプリの実際の TypeScript の合成コード**で各モードを仕上げて、HDR+ の完成写真と比べます。

```bash
cd training/eval
python make_brackets.py ../data/test scenes 1024
cd ../.. && EVAL_DIR=training/eval/scenes EVAL_OUT=training/eval/out npx vitest run --config training/eval/vitest.config.ts
cd training/eval && python metrics.py scenes out
python sheet.py scenes out sheet.jpg <シーン名>,<シーン名>,...
```

そのほかの確認用スクリプト:

- `analyze_model.py`: 係数の健全性（トーンカーブの逆転・傾きと彩度の範囲・露出への依存）
- `eval/make_jpeg_brackets.py`: カメラ JPEG 風（S 字のトーンカーブ + 8bit）のブラケットで同じ評価をする
- `eval/make_hires.py`: 長辺 2048px のシーンを作り、等倍で斑点やハロが出ないか確かめる

## 結果（同梱の `tone-hdrplus.bin`）

- データ: 3,640 シーン中 3,637 組を取り出し（除外 3）、学習 3,365・検証 119・評価 153（学習・検証には未使用）
- 学習: CPU（4 コア）で 40 エポック・約 85 分。検証 PSNR 25.85 dB（エポック 38、512px・リニア入力から直接）
- 係数の健全性（評価シーン 40 枚で確認）: トーンカーブの逆転 0%、傾き 0.28〜1.97、彩度 0.80〜2.0 倍、入力の露出を 4 倍にしても出力の差は最大 0.05

正則化（`curve_penalty`）の効果。正則化なしの試作では、学習画像にほとんど画素が来ない明るさの段の係数が極端な値
（傾き 0.003〜3667、彩度 0.003〜8.3 倍）になり、フル解像度で細部やノイズがそこへ入ると破綻するおそれがあった。
同じ条件（600 シーン・4 エポック）での比較:

| | 正則化なし | あり |
| --- | --- | --- |
| 検証 PSNR | 21.38 dB | 21.70 dB |
| トーンカーブの逆転 | 16% | 0.04% |
| 傾きの範囲 | 0.003〜3667 | 0.05〜1.86 |
| 彩度の範囲 | 0.003〜8.3 倍 | 1.02〜1.74 倍 |

評価シーン 153 枚で、カメラの AEB を模したブラケットをアプリの TypeScript コードで仕上げたときの、HDR+ の完成写真との差（長辺 1024px）:

| モード | PSNR | SSIM | ΔE (CIELAB) | 平均明度の差 |
| --- | --- | --- | --- | --- |
| 合成前（基準フレーム） | 19.20 dB | 0.644 | 12.91 | −1.1 |
| ナチュラル | 17.32 dB | 0.625 | 16.65 | +10.2 |
| HDR | 17.54 dB | 0.611 | 15.49 | +7.6 |
| おまかせ | 23.06 dB | 0.709 | 8.45 | −0.1 |

- 平均彩度は HDR+ の 1.01 倍（中央値 0.99）。1.25 倍を超えるのは 5% のシーンだけで、苦手なのは明暗差が小さく最初から色の濃い場面（例: 電球色の木の床）
- 同じ評価をカメラ JPEG 風のブラケット（S 字のトーンカーブ + 8bit）で行っても、仕上がりは破綻しなかった（RAW の方が正確）
- 2048px で作ったシーンを等倍で確認し、斑点やハロが出ないことを確かめた
